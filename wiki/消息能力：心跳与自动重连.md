# 消息能力：心跳与自动重连

长连接的可靠性由三部分组成：**心跳保活**、**超时探活**、**指数退避自动重连**，并针对移动端做了**前后台省电**处理。核心实现见 `HeartbeatManager` 与 `ImClient`。

## 心跳管理器 HeartbeatManager

连接认证（`AUTHENTICATED`）后，`ImClient` 创建并启动 `HeartbeatManager`：

```kotlin
HeartbeatManager(
    intervalMs = heartbeatIntervalMs,   // 心跳间隔，默认 15s
    timeoutMs  = heartbeatTimeoutMs,    // 响应超时，默认 20s
    onSend = { packet -> send(packet) },// 发送 HEARTBEAT_REQ
    onTimeout = { onHeartbeatTimeout() },// 超时 → 关 Socket → 触发重连
)
```

### 为什么用单线程 + wait/notify 而非 Timer

`java.util.Timer.cancel()` 无法取消已被 Timer 线程取出、正待执行的 `TimerTask`，会导致旧定时器"复活"、多个超时定时器并存，最终误报心跳超时触发断连。

`HeartbeatManager` 采用**单条 daemon 线程**串行执行"发送 → 等待响应（`lock.wait(timeoutMs)`）→ 休眠到下次计划时刻"，保证同一时刻只存在一个"待响应"窗口，不会出现旧定时器误触发。

```
循环（单线程）：
  synchronized(lock) {
    respReceived = false
    onSend(HeartbeatReq)
    lock.wait(timeoutMs)         // 收到响应被 notify，或超时返回
    ok = respReceived
  }
  if (!ok) onTimeout(); break     // 超时 → 断连重连
  sleep(interval - elapsed)       // 保持固定心跳间隔
```

收到 `HEARTBEAT_RESP` 时，`ImClient` 调用 `heartbeatManager.onHeartbeatResponse()`：置 `respReceived = true` 并 `notifyAll()` 唤醒心跳线程，重置超时窗口。

## 心跳间隔与服务端超时对齐

心跳间隔需 **≤ 服务端读空闲超时的一半**，为网络抖动留足余量。默认 15s 心跳 / 20s 超时适配常见服务端配置；请按服务端 `IdleStateHandler` 调整 `ImConfig.heartbeatIntervalMs` / `heartbeatTimeoutMs`。

## 超时与断连

心跳超时 `onHeartbeatTimeout()`：停止心跳、关闭 Socket、调用 `handleDisconnect()` 进入重连流程。读线程读到 EOF 或异常同样触发 `handleDisconnect()`。

## 自动重连：指数退避

`scheduleReconnect(generation)` 计算下次重连延迟：

```kotlin
val delay = (reconnectBaseDelayMs * 2.0.pow(attempts)).coerceAtMost(reconnectMaxDelayMs)
```

| 参数 | 默认 | 说明 |
|------|------|------|
| `reconnectBaseDelayMs` | 2000 | 基础间隔，第 n 次退避 = base × 2ⁿ |
| `reconnectMaxDelayMs` | 60000 | 退避封顶 |
| `maxReconnectAttempts` | null | 最大次数，null 表示无限重连 |

退避示例（base=2s, max=60s）：2s → 4s → 8s → 16s → 32s → 60s → 60s …

达到最大次数后停止并置 `DISCONNECTED`；连接成功后 `attempts` 归零。

## 并发与竞态防护

| 标志 | 作用 |
|------|------|
| `connectGeneration` | 每次 `connect()` 递增；旧的读线程退出/`disconnect()`/排队重连发现代次不匹配则跳过，避免误伤新连接 |
| `reconnectScheduled` | 同一时刻只允许一个排队重连任务，防止并发连接触发服务端**同设备互踢**形成无限重连循环 |
| `connecting` | `doConnect`/`doConnectSync` 互斥，保证同一时刻只有一个连接建立过程 |
| `disposed` | 已释放则不再重连 |
| `kicked` | 被踢下线后禁止自动重连（用户主动 `reconnectIfNeeded` 会重置） |

## 移动端省电：前后台

```kotlin
fun pauseForBackground()   // 置 backgrounded：重连改用 5 分钟固定间隔
suspend fun reconnectIfNeeded()  // 回前台：若已断开立即关闭旧 Socket 并 doConnect
```

- 后台时不再高频重试，降低电量与流量消耗。
- 回前台时 `reconnectIfNeeded` 先判断状态：`AUTHENTICATED`/`CONNECTED`/`CONNECTING` 直接跳过；否则重置计数、序号，立即重连。
- 若曾被踢（`kicked`），`reconnectIfNeeded` 会重置 `kicked` 允许用户主动重连。

## 实践建议

1. 监听 `connectionState` 向用户展示"连接中/已连接/重连中"。
2. `onBindFailed` 时区分 token 失效（跳登录）与网络异常（等待重连）。
3. `onKicked` 提示"账号在其他设备登录"，并停止后台重试直到用户确认。
4. 在 `Application`/前台 Service 的生命周期回调中调用 `pauseForBackground()` 与 `reconnectIfNeeded()`。
